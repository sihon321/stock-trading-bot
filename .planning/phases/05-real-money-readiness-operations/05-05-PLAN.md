<objective>
Close the single OPS-02 blocking gap from 05-VERIFICATION.md: the SQLite schema and `write_decision` writer already support a `confidence` column, but the production CLI run loop always passes `confidence=None` (cli.py:302), so the parsed LLM signal's confidence is never persisted end-to-end. Thread the parsed signal confidence from `execute_signal_cycle` out through `ExecutionResult`, have the CLI read `result.confidence`, and pin the behavior with an end-to-end test that observes the stored value round-trip through a real SQLite DB.

Purpose: OPS-02 requires that every cycle's LLM signal be written to the reviewable audit store; confidence is part of that signal (D-10) and is currently dropped. This restores audit completeness with the smallest possible change and no new trade logic.

Design decision (resolving the D-10 vs D-11 tension explicitly): confidence rides `ExecutionResult`, NOT `CycleAuditEvent`. `ExecutionResult` is the execution-layer result carrier that already holds `.audit` and `.broker_order_id`; adding one optional field to it leaves `CycleAuditEvent` a frozen stdlib dataclass with zero changes — honoring D-11 ("CycleAuditEvent stays the in-memory shape — no Phase 2 domain-type change; the writer is the sink") literally. It still satisfies D-10 ("persisted fields include parsed signal + confidence") because the writer now receives a real value. VERIFICATION.md's remediation explicitly permits carrying confidence via "the execution result/audit event OR another production-safe result field", so `ExecutionResult` is the sanctioned, smallest carrier. This does NOT re-open frozen Phase 2-4 trade logic, the risk engine, confidence gates, or the signal parser.

Output: a `confidence` field on `ExecutionResult`, a corrected CLI audit write, and an end-to-end confidence-persistence test.
</objective>
